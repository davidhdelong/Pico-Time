GPS Time Appliances

Firmware, timing architecture, synchronization logic, and operational behavior

This document describes the current time-server firmware in the project pico_gps_l76k. It covers the L76K NMEA appliance and the u-blox NEO-F10N UBX appliance, which share the same Pico hardware and timing engine but use different GPS message paths.

Executive summary. GPS supplies UTC identity and navigation data; the GPS 1-PPS edge supplies the precise repeating timing reference. A PIO hardware counter and DMA capture PPS intervals without depending on CPU interrupt latency. An alpha-beta servo estimates the PPS period and its slow drift, while the Pico creates a continuous high-resolution timebase used by the NTP server, dashboard, RTC logic, and display.

Prepared from the current source tree and deployed firmware behavior on September 3, 2026.

3. Startup and task ownership

At startup the firmware initializes the clocks, GPIO, RTC, GPS UART, PIO PPS capture, Wi-Fi, NTP server, HTTP server, and the high-resolution timebase. The Pico launches the second core so networking does not have to share the main GPS/timing loop.

Core 0 — timing and device control

  • Services GPS UART input and parses complete NMEA lines or UBX frames.
  • Polls the PPS DMA ring and consumes hardware-captured counter values.
  • Runs the PPS interval calculations and alpha-beta servo.
  • Updates UTC snapshots, RTC state, holdover logic, leap cache, and display state.
  • Feeds the watchdog.

Core 1 — network and Wi-Fi

  • Runs the CYW43 Wi-Fi driver polling loop.
  • Maintains the station connection and retry backoff.
  • Services lwIP TCP/IP processing.
  • Answers NTP requests and HTTP dashboard requests.
  • Updates the network LED output based on shared timing state.

Shared state is protected with the firmware’s statistics mutex or atomic counters. The network side reads a coherent health snapshot rather than directly racing the timing calculations.

4. GPS serial processing

L76K NMEA path

The L76K path collects UART bytes into bounded line buffers. At a newline, the line is queued with the high-resolution timestamp of its first byte. Checksum validation and sentence parsing then update GPS statistics.

  • RMC supplies UTC time/date, validity, speed, and position.
  • GGA supplies fix quality, satellites, altitude, and DOP data.
  • GSA/GSV supply additional constellation and satellite information, subject to what the L76K reports.

The firmware configures the L76K with PCAS commands: it trims unwanted output, changes the receiver baud rate, and leaves the desired NMEA output enabled.

u-blox UBX path

The UBX path feeds bytes into a checksum-validated binary frame parser. The deployed configuration enables these one-Hz messages on the receiver UART:

MessagePurpose
UBX-NAV-PVTValidated UTC date/time, fix type, position, DOP, and navigation solution.
UBX-TIM-TPTime-pulse metadata and timing quality information.
UBX-NAV-SATTotal/used satellite counts by constellation, including GPS, Galileo, BeiDou, GLONASS, QZSS, and SBAS.

The physical TIMEPULSE/PPS edge remains the high-precision reference. UBX serial data validates and labels that edge; it does not replace the edge capture.

5. PPS capture: PIO and DMA

The PPS input is connected to a PIO state machine. The PIO maintains a free-running 32-bit down-counter and captures its value on each rising PPS edge. Each captured value is pushed into the PIO FIFO. DMA transfers the FIFO values into a 16-entry ring buffer without requiring a CPU interrupt for every edge.

GPS PPS rising edge
        │
        ▼
PIO state machine: free-running counter → capture counter value → FIFO

                                      DMA endless ring buffer (16 samples)
                                                        │
                                                        ▼

At a configured 50 MHz counter rate, one counter tick represents 20 ns. The capture is therefore independent of the variable delay that would occur if the CPU timestamped the GPIO interrupt in software. DMA overrun count is exposed in the dashboard and is currently zero on both deployed devices.

Important distinction: PPS capture measures the interval between receiver edges. It does not by itself prove the absolute UTC phase of an edge. An interval that is 4 µs shorter than one second is a period/frequency observation, not proof that the edge is 4 µs late.

6. Alpha-beta time discipline

The servo is an estimator, not a step-by-step clock reset. It tracks two state variables:

  • Period estimate: the learned duration of one PPS interval.
  • Period-rate estimate: the slow change in that duration, representing oscillator drift.

For each accepted interval, the servo predicts the next period, computes the innovation, and applies two corrections:

prediction  = learned_period + learned_period_rate
innovation  = measured_interval - prediction
period      += innovation / 8
rate        += innovation / 64

The deployed gains are alpha = 1/8 and beta = 1/64. Alpha responds to phase/period discrepancies relatively quickly; beta changes the frequency estimate more slowly so the servo does not chase individual PPS noise.

Median and MAD rejection

A five-sample history is maintained. Once enough samples exist, the incoming interval is compared with the median. A sample is rejected when its residual exceeds max(50,000 ns, 6 × MAD). Rejected samples do not update the servo. This protects the estimate from a missed edge, a malformed capture, or a transient measurement.

7. High-resolution software time and UTC labeling

The RP2350 DWT cycle counter is used for a high-resolution monotonic timebase. It is anchored to the SDK microsecond clock and periodically re-anchored. This provides fine-grained timestamps for PPS, serial arrival, NTP receive/transmit processing, and internal scheduling.

The GPS message establishes the UTC date and second number. The next appropriate PPS edge is associated with that UTC second. After that, each PPS increments the UTC epoch by one second while the high-resolution clock supplies the fraction between edges.

The result is a continuous software clock:

UTC timestamp = GPS UTC epoch label + disciplined sub-second time from PPS

The GPS serial message is deliberately treated as delayed data. RMC-to-PPS latency is measured and learned for acceptance decisions, but UART delivery delay is not used as the PPS edge timestamp.

8. RMC/NAV message acceptance

GPS time is accepted only when the navigation data meets configured quality checks such as fix quality, satellite count, HDOP limits where available, checksum validity, and freshness. The RMC-to-PPS window protects against pairing a message from the wrong second with a PPS edge.

The window starts permissive during bootstrap so the firmware can learn the receiver’s normal UART delay. Once the delay is consistent, the window tightens toward the accuracy-mode limit of 20,000 µs. This window concerns serial message alignment; it is not the PPS accuracy.

9. RTC synchronization and holdover

The DS3231 is a secondary time source and backup oscillator. GPS/PPS remains primary while valid.

  1. GPS UTC and PPS establish the live time.
  2. The RTC is periodically synchronized rather than rewritten on every PPS edge.
  3. The RTC aging register is adjusted using a long-window drift estimate to avoid reacting to short-term noise.
  4. The SQW/1 Hz output is measured against GPS PPS. It must show multiple good aligned edges and approximately one minute of stable PPS before being trusted for holdover.
  5. If GPS disappears, the RTC SQW can provide the one-second holdover tick. The firmware returns to GPS/PPS when it becomes valid again.

GPS holdover begins after the configured GPS quality timeout (10 seconds by default). SQW trust requires four good edges and a 60-tick settling period. A large RTC phase error can trigger a scheduled rephase; this is separate from the live PPS servo.

10. Leap seconds and UTC policy

The firmware uses the IANA leap-seconds list. It first checks the RTC EEPROM cache and fetches the network copy when the cache is missing, invalid, or expired. Parsed metadata is stored back to EEPROM. The deployed network-facing policy is a linear 24-hour smear before a listed leap event.

  • GPS input is treated as the UTC identity source.
  • NTP timestamps and the display apply the configured smear policy when applicable.
  • The dashboard reports whether leap data is loaded, its source, expiration, and next event.

11. NTP server

The Pico listens on UDP port 123 and serves NTP client-mode requests. It timestamps receive and transmit processing with the disciplined high-resolution clock, returns the current source quality, and reports PPS as stratum 1 when PPS is valid.

PPSPrimary: GPS UTC label plus PPS-disciplined sub-second time.
RTC SQWSecondary holdover when GPS/PPS is unavailable but SQW is trusted.
Coarse GPS/RTCFallback only when a valid source exists without a trusted PPS/SQW edge.

Malformed packets, rate-limited requests, send errors, request counts, and network reconnects are counted and shown in the health JSON. The configured request limit is 20 NTP requests per second.

12. HTTP dashboard and diagnostics

The HTTP server is enabled by default on port 80. The dashboard polls /api/health approximately once per second and includes a timeout plus overlap protection so a slow request cannot create an unlimited queue of browser requests.

The health endpoint exposes GPS, PPS, servo, RTC, leap, Wi-Fi, NTP, HTTP, and watchdog-relevant counters. The most important timing fields are:

16. Bottom line

The architecture is sound for a network time appliance: serial GPS data supplies UTC identity, hardware PPS supplies the second boundary, PIO/DMA removes CPU interrupt latency from the measurement, and the alpha-beta servo maintains a continuous clock between edges. The RTC provides disciplined backup holdover, while the NTP and HTTP services consume snapshots of that timing state.

The most important diagnostic rule is to keep three concepts separate: period error is deviation from an ideal one-second interval, jitter is short-term variation around the learned interval, and absolute UTC phase requires an independent timing comparison. The current dashboard now reports the first two separately and exposes servo innovation to make that distinction visible.

This document intentionally omits network credentials. Pin assignments and defaults are documented from the current source; compile-time overrides remain possible through CMake definitions.
